# Feature Specification: 키움증권 REST API 기반 자동매매 에이전트

**Feature Branch**: `001-kiwoom-auto-trading`
**Created**: 2025-11-22
**Status**: Draft
**Input**: User description: "나만의 투자 전략을 수행하는 키움증권 REST API 기반 자동매매 에이전트"

## 개요

사용자가 정의한 투자 전략에 따라 자동으로 주식 매매를 수행하는 서버 기반 자동매매 시스템. 키움증권 REST API를 통해 실시간 시장 데이터를 수집하고, 사전 정의된 매매 로직에 따라 자동으로 주문을 실행하며, 사용자가 HTS 앞에 앉아있지 않아도 24시간 시장을 감시하고 거래할 수 있도록 지원한다.

## 목적 및 가치

### 왜 이 시스템이 필요한가

1. **심리적 요인 배제**: 공포와 탐욕에 의한 뇌동매매를 방지하고 기계적인 원칙 매매를 통해 전략의 일관성 유지
2. **시간적 자유 확보**: 전업 투자자가 아니어도 시스템이 수천 개 종목을 지속적으로 모니터링
3. **전략 검증 및 고도화**: 막연한 감이 아닌 데이터와 로직 기반 투자로 복합적인 분석과 전략 구현 가능

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 전략 기반 자동 매수/매도 실행 (Priority: P1)

사용자는 사전에 정의한 매매 전략(예: 골든크로스 발생 시 매수, -3% 손절)을 시스템에 설정하면, 시스템이 장 운영 시간 동안 자동으로 시장을 감시하고 조건 충족 시 매수/매도 주문을 실행한다.

**Why this priority**: 자동매매 시스템의 핵심 가치를 제공하는 가장 중요한 기능. 이것만으로도 사용자에게 즉각적인 가치를 제공할 수 있다.

**Independent Test**: 특정 전략(예: 단순 이동평균선 골든크로스)을 설정하고 시뮬레이션 모드로 실행하여 조건 충족 시 주문이 정확히 발생하는지 독립적으로 검증 가능. 실제 계좌 연동 없이도 테스트 가능.

**Acceptance Scenarios**:

1. **Given** 사용자가 "5일 이평선이 20일 이평선을 상향 돌파 시 매수" 전략을 설정했을 때, **When** 대상 종목에서 골든크로스가 발생하면, **Then** 시스템은 자동으로 해당 종목에 대한 매수 주문을 실행한다
2. **Given** 보유 종목의 현재가가 매수가 대비 -3% 이하로 하락했을 때, **When** 손절 조건이 충족되면, **Then** 시스템은 자동으로 해당 종목을 매도한다
3. **Given** 여러 종목이 동시에 매수 조건을 충족했을 때, **When** 가용 예수금이 제한적이면, **Then** 시스템은 우선순위 규칙에 따라 일부 종목만 매수한다
4. **Given** 장 마감 10분 전 상황에서, **When** 새로운 매수 조건이 충족되면, **Then** 시스템은 신규 매수 주문을 차단하고 사용자에게 "장 마감 임박으로 인한 매수 차단" 알림을 전송한다

---

### User Story 2 - 계좌 상태 및 포지션 모니터링 (Priority: P1)

사용자는 언제든지 현재 시스템의 운영 상태, 보유 종목 현황, 예수금, 손익 현황을 확인할 수 있다.

**Why this priority**: 자동매매 시스템을 안심하고 운영하려면 실시간 상태 확인이 필수적이다. P1 핵심 기능과 함께 초기 MVP에 포함되어야 사용자가 시스템을 신뢰할 수 있다.

**Independent Test**: 시스템 대시보드에 접속하여 계좌 잔고, 보유 종목, 평가손익 정보가 정확히 표시되는지 확인. API 연결 없이 목(mock) 데이터로도 UI 테스트 가능.

**Acceptance Scenarios**:

1. **Given** 시스템이 정상 작동 중일 때, **When** 사용자가 계좌 현황을 조회하면, **Then** 현재 예수금, 보유 종목 목록, 각 종목의 평가손익이 실시간으로 표시된다
2. **Given** 시스템이 주문을 실행했을 때, **When** 주문이 체결되면, **Then** 계좌 현황이 자동으로 업데이트되고 사용자에게 알림이 전송된다
3. **Given** API 연결이 일시적으로 끊어졌을 때, **When** 사용자가 계좌 조회를 시도하면, **Then** 시스템은 마지막으로 알려진 상태와 함께 "연결 불안정" 경고 메시지를 표시한다

---

### User Story 3 - 전략 유연성 및 교체 (Priority: P2)

사용자는 운영 중인 전략을 중단하고 새로운 전략으로 교체하거나, 여러 전략을 동시에 운영할 수 있다.

**Why this priority**: 시장 상황 변화에 따라 전략을 바꿀 수 있는 능력은 중요하지만, 초기 MVP에서는 하나의 전략만 운영해도 핵심 가치를 제공할 수 있다.

**Independent Test**: 기존 전략을 중지하고 새로운 전략 모듈을 로드한 후, 새 전략의 조건으로 주문이 발생하는지 확인. 전략 간 독립성 검증.

**Acceptance Scenarios**:

1. **Given** 사용자가 "스캘핑 전략"을 운영 중일 때, **When** "스윙 트레이딩 전략"으로 교체하면, **Then** 기존 전략은 중단되고 새 전략이 활성화된다
2. **Given** 사용자가 여러 전략을 설정했을 때, **When** 각 전략에 자금 배분 비율을 지정하면, **Then** 시스템은 각 전략에 할당된 자금 범위 내에서만 주문을 실행한다
3. **Given** 새로운 전략 모듈이 추가되었을 때, **When** 시스템에 로드하면, **Then** 기존 운영 중인 전략에 영향 없이 독립적으로 작동한다

---

### User Story 4 - 실시간 시장 데이터 수집 및 처리 (Priority: P1)

시스템은 키움증권 REST API를 통해 실시간 체결 데이터와 과거 차트 데이터(일봉/분봉)를 수집하고 전략 판단에 활용한다.

**Why this priority**: 데이터 수집 없이는 어떤 매매 판단도 불가능하므로 P1 필수 기능이다.

**Independent Test**: 특정 종목의 실시간 가격 데이터를 1분간 수집하고, 수신된 데이터가 누락 없이 정확한지 검증. API 응답 시뮬레이터로 독립 테스트 가능.

**Acceptance Scenarios**:

1. **Given** 시스템이 특정 종목을 감시 대상으로 등록했을 때, **When** 해당 종목의 거래가 체결되면, **Then** 실시간 체결 데이터(가격, 거래량, 시간)가 즉시 수집된다
2. **Given** 전략이 과거 20일간의 일봉 데이터를 필요로 할 때, **When** 시스템이 시작되면, **Then** 필요한 과거 데이터를 API로부터 조회하여 메모리에 로드한다
3. **Given** 장 운영 시간 동안, **When** API 서버 응답이 지연되거나 실패하면, **Then** 시스템은 최대 3회 재시도하고, 실패 시 해당 종목의 데이터 수집을 일시 중단하며 관리자에게 알림을 보낸다

---

### User Story 5 - 안전한 주문 실행 및 위험 관리 (Priority: P1)

시스템은 주문 전 예수금을 확인하고, 중복 주문을 방지하며, API 통신 오류 시 안전하게 처리한다.

**Why this priority**: 실제 돈이 오가는 시스템이므로 안전성은 핵심 가치의 일부이며 P1에 포함되어야 한다.

**Independent Test**: 예수금이 부족한 상태에서 매수 시도, 동일 종목 중복 주문 시도, API 타임아웃 상황을 시뮬레이션하여 시스템의 안전 장치 작동 확인.

**Acceptance Scenarios**:

1. **Given** 매수 조건이 충족되었을 때, **When** 주문 직전 예수금을 확인한 결과 잔액이 부족하면, **Then** 주문을 취소하고 사용자에게 알림을 보낸다
2. **Given** 특정 종목에 대해 매수 주문이 이미 전송되었을 때, **When** 동일 종목에 대해 다시 매수 조건이 충족되면, **Then** 기존 주문이 체결되거나 취소되기 전까지 추가 주문을 차단한다
3. **Given** API 주문 요청을 전송했을 때, **When** 네트워크 오류나 타임아웃이 발생하면, **Then** 최대 2회 재시도하고, 실패 시 주문을 취소 상태로 기록하며 사용자에게 긴급 알림을 전송한다
4. **Given** 시스템이 운영 중일 때, **When** 총 손실이 일일 손실 한도(예: 계좌 잔고의 5%)를 초과하면, **Then** 모든 자동 매매를 즉시 중단하고 사용자에게 알림을 보낸다

---

### User Story 6 - 시스템 헬스 체크 및 자가 진단 (Priority: P2)

시스템은 자신의 상태를 주기적으로 점검하고, API 연결 상태, 데이터 수신 정상 여부를 확인하며 이상 발생 시 사용자에게 알린다.

**Why this priority**: 신뢰성 향상을 위해 중요하지만, 초기에는 수동 모니터링으로 대체 가능하여 P2로 설정.

**Independent Test**: API 연결을 강제로 끊거나 데이터 스트림을 중단한 후, 시스템의 헬스 체크 로직이 이상을 감지하고 알림을 보내는지 확인.

**Acceptance Scenarios**:

1. **Given** 시스템이 정상 작동 중일 때, **When** 매 1분마다 헬스 체크를 실행하면, **Then** API 연결 상태, 마지막 데이터 수신 시간, 주문 실행 가능 여부를 점검하고 로그에 기록한다
2. **Given** API 연결이 5분 이상 끊어졌을 때, **When** 헬스 체크가 실행되면, **Then** "API 연결 불가" 상태로 전환하고 사용자에게 즉시 알림을 전송한다
3. **Given** 장 운영 시간인데 데이터 수신이 3분 이상 없을 때, **When** 헬스 체크가 실행되면, **Then** "데이터 수신 이상" 경고를 발생시키고 API 재연결을 시도한다

---

### User Story 7 - 알림 및 트레이딩 리포팅 (Priority: P2)

시스템은 주요 이벤트(주문 체결, 오류 발생, 장 마감 등) 발생 시 사용자에게 알림을 보내고, 일일 트레이딩 결과를 요약하여 제공한다.

**Why this priority**: 사용자 경험 향상을 위해 중요하지만, 초기에는 로그 확인으로 대체 가능하여 P2로 설정.

**Independent Test**: 주문 체결 이벤트를 시뮬레이션하여 알림이 정확히 전송되는지, 일일 리포트가 올바르게 생성되는지 확인.

**Acceptance Scenarios**:

1. **Given** 매수 주문이 체결되었을 때, **When** 체결 확인 이벤트가 발생하면, **Then** 사용자에게 "[종목명] 매수 체결: [수량]주 @ [가격]원" 형식의 알림을 전송한다
2. **Given** 장 마감 후, **When** 시스템이 일일 트레이딩을 종료하면, **Then** 당일 총 매매 건수, 실현 손익, 보유 종목 현황을 요약한 리포트를 생성하여 사용자에게 전송한다
3. **Given** 시스템 오류가 발생했을 때, **When** 자동 복구가 불가능한 상황이면, **Then** 사용자에게 긴급 알림과 함께 상세 오류 내용을 전송한다

---

### Edge Cases

- **API 연결 불안정**: 키움증권 API 서버 장애나 네트워크 불안정 시 어떻게 대응하는가? → 재연결 로직과 대기 상태 전환
- **장 시작/종료 시간 처리**: 프리마켓, 장 시작, 장 마감, 시간외 거래 등 각 시간대별로 시스템 동작이 달라져야 하는가? → 시간대별 운영 모드 설정 (장 마감 10분 전부터 신규 매수 차단)
- **동시 다발적 조건 충족**: 수십 개 종목이 동시에 매수 조건을 충족했을 때 우선순위는? → 우선순위 알고리즘 및 자금 배분 규칙
- **주문 미체결 상황**: 주문을 전송했으나 장시간 체결되지 않을 때 어떻게 처리하는가? → 주문 취소 및 재주문 로직
- **급격한 가격 변동**: 서킷브레이커, VI(변동성완화장치) 발동 시 시스템 동작은? → 특수 상황 감지 및 매매 일시 중단
- **예수금 부족**: 여러 전략이 동시에 자금을 필요로 할 때 배분은? → 전략별 자금 할당 및 우선순위
- **보유 종목 손절 vs 신규 매수**: 손절 조건과 신규 매수 조건이 동시에 발생할 때 순서는? → 손절 우선 실행 정책
- **데이터 누락**: 특정 종목의 데이터가 일시적으로 수신되지 않을 때 전략 판단은? → 불완전 데이터 처리 규칙

## Requirements *(mandatory)*

### Functional Requirements

#### 데이터 수집 및 처리

- **FR-001**: 시스템은 키움증권 REST API를 통해 실시간 주식 체결 데이터(현재가, 거래량, 호가)를 수집해야 한다
- **FR-002**: 시스템은 과거 차트 데이터(일봉, 분봉)를 요청하고 저장할 수 있어야 한다
- **FR-003**: 시스템은 수집된 데이터를 전략 엔진이 사용할 수 있는 형식으로 가공해야 한다
- **FR-004**: 시스템은 데이터 수신 중 오류 발생 시 최대 3회 재시도해야 한다
- **FR-005**: 시스템은 감시 대상 종목 목록을 사용자가 설정할 수 있어야 한다

#### 전략 관리

- **FR-006**: 시스템은 사용자가 정의한 매매 전략을 로드하고 실행할 수 있어야 한다
- **FR-007**: 시스템은 여러 전략을 독립적으로 운영할 수 있도록 전략을 모듈화해야 한다
- **FR-008**: 시스템은 운영 중 전략을 중단하거나 교체할 수 있어야 한다
- **FR-009**: 각 전략은 자신의 매수/매도 조건을 독립적으로 평가해야 한다
- **FR-010**: 시스템은 전략별로 사용 가능한 자금 한도를 설정할 수 있어야 한다

#### 주문 실행 및 관리

- **FR-011**: 시스템은 매수 주문 전 반드시 예수금(매수 가능 금액)을 확인해야 한다
- **FR-012**: 시스템은 동일 종목에 대한 중복 주문을 방지해야 한다
- **FR-013**: 시스템은 주문 전송 후 체결 여부를 확인하고 미체결 주문을 관리해야 한다
- **FR-014**: 시스템은 API 통신 실패 시 최대 2회 재시도하고, 실패 시 주문을 취소 상태로 기록해야 한다
- **FR-015**: 시스템은 시장가, 지정가 주문을 모두 지원해야 한다

#### 위험 관리

- **FR-016**: 시스템은 일일 손실 한도를 설정하고, 한도 초과 시 모든 자동 매매를 중단해야 한다
- **FR-017**: 시스템은 종목별 손절 조건을 설정하고 자동 실행할 수 있어야 한다
- **FR-018**: 시스템은 보유 종목의 평가 손익을 실시간으로 계산해야 한다
- **FR-019**: 시스템은 총 투자 금액 대비 최대 위험 노출 비율을 제한할 수 있어야 한다

#### 계좌 및 포지션 관리

- **FR-020**: 시스템은 현재 계좌 잔고(예수금)를 조회할 수 있어야 한다
- **FR-021**: 시스템은 보유 종목 목록과 각 종목의 수량, 평균 매수가를 조회할 수 있어야 한다
- **FR-022**: 시스템은 주문 체결 시 계좌 상태를 자동으로 업데이트해야 한다

#### 시스템 모니터링 및 안정성

- **FR-023**: 시스템은 주기적(1분 간격)으로 자가 진단을 수행해야 한다
- **FR-024**: 시스템은 API 연결 상태를 지속적으로 확인하고 연결 끊김 시 자동 재연결을 시도해야 한다
- **FR-025**: 시스템은 데이터 수신이 일정 시간(3분) 이상 없을 때 경고를 발생시켜야 한다
- **FR-026**: 시스템은 모든 주문 실행 내역과 오류 발생 내역을 로그로 기록해야 한다
- **FR-027**: 시스템은 장 운영 시간을 인식하고, 장 시작 전/장 중/장 마감 후에 따라 다르게 동작해야 한다 (특히, 장 마감 10분 전부터 신규 매수 주문을 차단해야 한다)

#### 알림 및 리포팅

- **FR-028**: 시스템은 주문 체결 시 사용자에게 알림을 전송해야 한다
- **FR-029**: 시스템은 중요한 오류 발생 시 사용자에게 긴급 알림을 전송해야 한다
- **FR-030**: 시스템은 일일 트레이딩 종료 후 거래 내역 요약 리포트를 생성해야 한다
- **FR-031**: 시스템은 디스코드(Discord) 웹훅과 이메일을 통해 알림을 전송해야 하며, 사용자가 사용할 채널을 선택할 수 있어야 한다

#### 운영 및 설정

- **FR-032**: 시스템은 설정 파일을 통해 전략, 종목, 위험 관리 규칙을 변경할 수 있어야 한다
- **FR-033**: 시스템은 수동 개입 모드를 지원하여 자동 매매를 일시 중지하고 수동으로 주문을 실행할 수 있어야 한다
- **FR-034**: 시스템은 과거 데이터 기반 백테스팅 모드를 제공하여 실제 주문 없이 전략을 검증할 수 있어야 한다 (실시간 종이 거래 기능은 향후 추가 예정)

### Key Entities

- **전략(Strategy)**: 매수/매도 조건을 정의하는 논리 단위. 각 전략은 독립적으로 종목을 감시하고 주문을 생성한다. 속성: 전략명, 감시 종목 목록, 매수 조건, 매도 조건, 할당 자금
- **종목(Stock)**: 거래 대상 주식. 속성: 종목코드, 종목명, 현재가, 거래량, 차트 데이터(일봉/분봉)
- **주문(Order)**: 매수/매도 요청 단위. 속성: 주문번호, 종목코드, 주문유형(매수/매도), 주문가격, 주문수량, 주문시간, 체결상태, 체결가격, 체결수량, 체결시간
- **포지션(Position)**: 현재 보유 중인 종목. 속성: 종목코드, 보유수량, 평균 매수가, 현재가, 평가손익, 수익률
- **계좌(Account)**: 사용자의 증권 계좌 정보. 속성: 계좌번호, 예수금(현금), 총 평가금액, 총 손익
- **알림(Notification)**: 사용자에게 전달되는 메시지. 속성: 알림 유형(체결/오류/일일리포트), 메시지 내용, 발생시간, 전송 상태
- **시스템 상태(System Status)**: 시스템의 현재 운영 상태. 속성: API 연결 상태, 마지막 데이터 수신 시간, 운영 모드(정상/일시중지/오류), 활성 전략 목록

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 시스템은 장 운영 시간(09:00-15:30) 동안 99% 이상 안정적으로 작동해야 한다 (API 연결 유지율 기준)
- **SC-002**: 매수/매도 조건 충족 시 5초 이내에 주문이 실행되어야 한다 (조건 감지부터 API 주문 전송까지)
- **SC-003**: 사용자는 주문 체결 후 10초 이내에 알림을 수신해야 한다
- **SC-004**: 시스템은 예수금 부족이나 중복 주문 등의 오류 상황에서 잘못된 주문이 실행되지 않아야 한다 (오류 방지율 100%)
- **SC-005**: 사용자는 전략 교체 작업을 1분 이내에 완료할 수 있어야 한다 (전략 중지 → 새 전략 로드 → 재시작)
- **SC-006**: 시스템은 최소 50개 종목을 동시에 감시하고 분석할 수 있어야 한다
- **SC-007**: API 연결 끊김 발생 시 30초 이내에 자동 재연결을 시도하고 복구해야 한다
- **SC-008**: 일일 손실 한도 초과 시 즉시(1초 이내) 모든 자동 매매가 중단되어야 한다
- **SC-009**: 사용자는 일일 트레이딩 리포트를 통해 당일 총 손익, 매매 건수, 승률을 명확히 파악할 수 있어야 한다
- **SC-010**: 백테스팅 모드에서 과거 1년치 데이터로 전략을 검증할 수 있어야 한다

### Quality Attributes

- **신뢰성**: 시스템 오류로 인한 잘못된 주문이 발생하지 않아야 하며, 모든 주문은 명확히 추적 가능해야 한다
- **안전성**: 예수금 초과 주문, 중복 주문, 손실 한도 초과 등의 위험 상황을 사전에 차단해야 한다
- **투명성**: 모든 매매 결정 과정과 주문 실행 내역이 로그로 기록되고 사용자가 확인할 수 있어야 한다
- **유연성**: 새로운 전략을 쉽게 추가하거나 기존 전략을 수정할 수 있어야 한다

## Assumptions

- 사용자는 키움증권 계좌를 보유하고 있으며, REST API 사용 권한이 있다고 가정한다
- 키움증권 REST API는 안정적으로 운영되며, 공식 문서에 명시된 응답 시간 및 제한 사항을 준수한다고 가정한다
- 시스템은 24시간 구동 가능한 서버 환경에서 실행되며, 인터넷 연결이 안정적이라고 가정한다
- 사용자는 매매 전략의 개념을 이해하고 있으며, 스스로 매수/매도 조건을 정의할 수 있다고 가정한다
- 시스템은 한국 주식 시장의 정규 장 운영 시간(09:00-15:30)을 기준으로 동작한다 (시간외 거래는 초기 범위 외)
- 초기 버전에서는 현물 주식 매매만 지원하며, 선물/옵션/신용거래는 지원하지 않는다
- 알림 전송은 디스코드 웹훅과 이메일을 사용한다고 가정한다 (구체적 방식은 FR-031 참조)
- 백테스팅은 과거 데이터 기반 시뮬레이션만 지원하며, 실시간 종이 거래는 향후 버전에서 추가 예정이다 (FR-034 참조)
- 장 마감 10분 전부터는 신규 매수 주문을 차단하여 마감 직전 리스크를 최소화한다

## Dependencies

- 키움증권 REST API의 가용성 및 안정성에 의존한다
- 시장 데이터 제공 속도 및 정확성은 키움증권 API 서버 성능에 영향을 받는다
- 알림 전송은 외부 서비스(이메일 서버, 디스코드 웹훅 API)에 의존한다

## Out of Scope

초기 버전에서 다음 사항은 범위 외로 한다:

- 선물, 옵션, 신용거래 등 파생상품 매매
- 해외 주식 거래
- 복잡한 AI/머신러닝 기반 전략 (단순 기술적 지표 기반 전략만 지원)
- 실시간 차트 UI 제공 (데이터 수집 및 전략 실행에 집중)
- 모바일 앱 (웹 또는 CLI 기반 인터페이스 우선)
- 소셜 트레이딩 기능 (다른 사용자의 전략 공유/복사)
